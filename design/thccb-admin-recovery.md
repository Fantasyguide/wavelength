**管理员菜单与 THCCB 联动恢复：设计与决策**

日期：2026-10-23。两端实现、隔离验证和操作者实测已通过。下文保留设计取舍，最终行为与验证见 `thccb-admin-recovery-validation.md`；THCCB 正式部署独立安排。

本地审查基线：`469502a`。THCCB 接口审查依据：此前获取的正式站接口定义、正式站前端资源，以及官方仓库 `e69dd23e590019b885603f617a80d2c8a97374d6` 的联动实现；配套实现前应重新核对目标分支与部署版本。

**要达到的行为**

只要操控端仍能访问本地游戏服务器，关闭联动、作废本轮、重置本局就不等待 THCCB 返回。管理操作先改变本地游戏状态，THCCB 的取消和退款完成情况单独显示。对方掉线期间不能宣称退款已经完成，但不得因此锁住主游戏。

用户已批准：正常关键操作等待确认；允许揭晓后作废本地成绩并保留远端奖励；两端配套改造。并要求所有发钱走既有可审计路径。

**操控端界面**

顶部“重新开始”改为“管理员”。菜单在本地打开，不依赖远端请求，也不因普通游戏操作正在等待而禁用。联网时仅已认证控制器能操作；沿用现有共享密码权限，不另增管理员账号。监视器不显示操作菜单。本机模式保留惩罚、作废和重置，不显示 THCCB 操作。

| 菜单项 | 拟定行为 |
| --- | --- |
| 说话处罚 | 从讨论区移入菜单；仅讨论阶段且尚未锁定时可用。沿用随机游标并锁定的规则，确认后只执行一次。 |
| THCCB 联动开关 | 局中可切换。关闭立即解除本轮对 THCCB 的依赖，同时安排取消未结束竞猜；重新开启进入等待合适开盘时机的状态。 |
| 重试联动 | 移入菜单，先核对远端状态，再重试仍然需要的操作。处理中显示进度，但不禁用关闭联动、作废和重置。 |
| 作废本轮 | 确认后保留本局及当前出题队，撤销本轮成绩，重新抽题和目标，轮次序号不增加。旧竞猜另行处理。 |
| 重置本局 | 本局尚未按规则结束时可用。确认后清空本局成绩和复盘，回到开局设置，保留队名、题库和规则偏好；联动开关保持用户选择。 |

正常终局弹窗及返回复盘后的主操作区均提供“再来一局”，沿用同一开新局流程。作废当前轮若导致撤销刚产生的终局判定，按本轮开始前快照恢复；已经开始新轮或新局后，不回退更早轮次。

用户明确：“按钮下面”指“目标在左”等游戏操作按钮下方：状态在菜单关闭时也能看到。显示短句，如“已开盘”“等待转录员关上遮挡条”“本轮不联动”“本地已重置，旧竞猜退款待同步”。长错误和轮号放在菜单详情内。顶部连接徽标只表示接口可达性，不能用连接成功掩盖未完成的取消或结算。

取消、退款或冲突需要确认时，由菜单内的状态详情提供相应操作，不要求手工复制轮号或发送 HTTP 请求。前端管理菜单及确认框必须保持稳定，避免 SSE 更新重建 DOM 导致焦点或点击目标丢失。

**局中断开与重连**

- 关闭开关立即生效，并保存该选择。它阻止新的竞猜通知；已经安排的取消/退款处理仍可在后台联系 THCCB。
- 如果出题完成、锁定或揭晓正在等待 THCCB，关闭联动后，按该次已确认的本地操作继续；作废和重置则丢弃该待处理操作，不在新轮重放。
- 封盘等待解除后给足对方猜左右时间。其他阶段保留其合理剩余时间；作废和重置按新阶段重新计时。
- 出题阶段重新开启，允许在接下来这次“出题完成、关上遮挡条”时开盘；遮挡条已经关闭时重新开启，不补开当前竞猜，等下一次合适的关闭事件。
- 出题直接超时并跳入锁定、没有实际竞猜时段时，不瞬间补开再封盘。
- 如果到了开盘时机，旧竞猜取消仍未确认，则这一轮本地照常进行，标记为“不联动”；处理完成后也不在讨论中途补开，继续等待下一次合适事件。
- 对不上轮号、竞猜已经取消、当前轮明确不联动时，不展示引导观众对本轮下注的二维码；展示简短暂停说明。已取消或作废轮次的迟到榜单不能重新出现。

**作废本轮和计分**

本轮开始时保留可回退的内部快照，包括双方成绩、当前队伍、补轮状态、加时成绩/出手机会、胜负判定、复盘记录和本轮使用的重抽机会。作废恢复这份快照，再按照当前出题模式抽取新题和新目标。二选一回到选题；经典单题回到出题。题库充足时避开本次废弃题目；小题库允许无法避开的重复。目标重新随机采样，不把“随机”误解为保证数值永不重复。

不能仅把本轮得分从总分减掉：当前规则还会改变补轮、加时、提前结束和胜负判定。目标采样的内部历史也要恢复或替换，废弃轮不能被计作额外的一次出手机会。

本地显示的轮次保持不变，但每次重开都生成新的尝试标识和 THCCB 轮号。作废日志与有效得分复盘分开记录，便于解释资金结算与本地成绩不同的情况。

THCCB 当前只允许取消 `open` / `closed` 轮次；已经 `settled` 的奖励不能通过取消接口撤回。重复同样的取消或结算不会重复发钱。还要处理“结果请求已经到达对方，但响应尚未回来”的情况：前端不知道结果，不等于对方还没结算。

推荐：允许作废当前轮的本地成绩；若 THCCB 已结算，则保留其奖励，并在确认框与记录中明确说明。若结算情况未知，仍可立即作废本地，随后核对，显示“竞猜结算状态待确认”，不能承诺一定退款。未发送的结算任务被取消意图取代；已经发出的请求按远端最终状态处理。

**操作队列与高优先级处理**

当前 `intentSerial` 把外部 HTTP 等待包在全局串行队列里，需要重构，而不只是把管理按钮排到队头。

推荐拆为三部分：

1. 本地游戏状态的短事务：校验权限、轮次和操作，更新状态，立即推送，不在其中等待 THCCB。
2. 当前轮的待确认操作：保存操作内容和对应游戏/轮次标识，后台等待确认；同一轮的开盘、封盘、提交答案仍遵守先后顺序。
3. 独立的取消与恢复任务：管理操作可以立即作废旧待确认操作，并登记取消；同一站点清理旧竞猜优先于新开盘。

管理请求采用独立入口或明确的高优先级调度，处理完本地短事务即响应。所有相关命令携带操作 ID、游戏标识和轮次尝试标识，防止双击、多控制器和断线重发把重置后的新轮再次作废。旧轮拖动、旧倒计时和旧请求响应不允许修改新轮。

正常操作等待 THCCB 时，仅冻结对应的阶段转换和已提交输入。展开规则、打开管理员菜单以及管理操作仍然可用；锁定确认中不再接受游标变化，惩罚随机结果不会因重试重新抽取。

管理员指令不得放进前端通用的断线操作缓存，避免稍后重连时突然执行一次过时重置。HTTP 已成功而 SSE 稍后恢复时，按操作 ID 和最新状态确认，不重复执行。

可以中止本地在途 HTTP 请求，但中止不能撤销远端已经执行的业务。旧请求返回后，只能更新其自身的后台处理记录；不能重新开盘当前轮、清除新的错误或回退界面。

**后台任务与重启恢复**

新增私有持久记录，保存联动轮号、请求内容、已确认状态、取消/结算意图、重试时间和必要的操作关联。记录不会进入公共 SSE 或静态文件服务，也不把密钥写入浏览器。需要持久化的答案仅在服务端保存。

明确取消的任务采用有上限的退避间隔重试，并允许控制器立即重试。开盘失败不在本轮已经失效后盲目补发；新轮开始也不能删除旧轮尚未完成的退款任务。关闭再开启开关不会撤销之前的退款请求。

进程重启后先读取待处理记录并核对远端。已持久记录的明确取消/结算意图继续处理；仅有旧活动竞猜而没有恢复局势的，显示为待处理，在控制器提供取消并退款。本次不把“完整对局断电续玩”作为必需范围，但不能再次丢掉旧竞猜的身份。

地址和密钥仍留在高级设置，避免与局中开关混为一谈；存在待处理记录时，不能直接覆盖其联系目标或所需凭据。磁盘写入失败必须明确报告，不能伪称退款任务已可靠保存。

**操控端可解决的状态不匹配**

| 现场情况 | 处理方式 |
| --- | --- |
| 同一轮远端已开盘或已封盘，本地没收到响应 | 查询并补齐本地确认，不重复创建竞猜。 |
| 本地等待取消，远端已经取消 | 视为取消完成，更新退款摘要。 |
| 本地待确认轮在远端不存在 | 区分“确实不存在”和“请求可能迟到”；提供清理，不制造一轮竞猜来解锁。 |
| 远端仍是另一轮未结束竞猜 | 显示题目、轮次和状态，提供“取消旧竞猜并退款”的明确确认操作；不自动取消无法确认来源的其他对局。 |
| 本地已作废，但远端已经结算 | 标记“本地已作废，竞猜奖励保留”，停止无意义的取消重试。 |
| 密钥错误、站点地址错误、功能关闭 | 显示具体可操作原因；保留本地管理能力，不无限重发相同请求。 |
| 网络不可达 | 本地管理操作完成，显示“取消/退款待同步”，恢复后处理。 |

不得把所有 HTTP 404 都当成“取消成功”：THCCB 功能关闭或路径错误也可能返回 404。不得只看 HTTP 200；应核对返回轮号、实际状态和业务字段。

**是否配套修改 THCCB：两种可行范围**

| 范围 | 能达到的效果 | 限制 |
| --- | --- | --- |
| 只改本地 | 管理操作不被 THCCB 阻塞；后台补偿；处理多数旧轮冲突；本地计分回退与新菜单。 | 现有 `/current` 只返回最新轮；未知轮取消返回 404。无法严格解决取消先到、旧开盘请求后来才执行的竞态，需要保留不确定记录与反复核对。 |
| 两端配套修改（推荐） | 在上述基础上，可以可靠查询指定轮号，并让已取消的轮号不再被迟到的开盘请求创建。 | 需要 THCCB 后端接口、持久记录/迁移和配套测试；分步部署并保留兼容能力。 |

推荐的 THCCB 增量：

- 增加使用联动凭据按指定轮号查询状态的接口，返回开盘、封盘、已结算、已取消或明确不存在，以及适当的退款摘要。
- 支持对尚未创建的轮号登记取消意图；之后同轮号的开盘请求不得创建有效竞猜。取消与开盘必须在数据库层面正确协调，不能只靠单进程内锁或一次“先查询”。
- 给关键错误增加稳定的机器可识别代码，区分轮次不存在、联动未启用、上一轮未结束和已经结算，兼容已有展示文案。
- 保持已结算奖励不能撤回的规则；本次不引入账户余额追缴或财务逆向结算。

就算两端配套改造，THCCB 完全离线时仍不可能即时完成远端取消和退款；可保证的是本地立即继续，取消意图不会丢失，远端恢复后按协议完成处理。

**正常操作的两种策略**

推荐保留正常开盘、封盘、揭晓的确认要求，但把等待移出全局游戏队列。故障时，主持人可以关闭联动继续当前轮，也可作废或重置；三种管理操作均不等待 THCCB。

备选是主游戏始终自动推进，联动失败就自动取消该轮竞猜。这个方案需要更强的自动处理策略，尤其要保证封盘未确认时不会一边公开答案，一边继续把远端竞猜当作可正常结算；因此与“正常等待、管理员决定”相比，行为改变更大。

**实现与验证顺序**

1. 确认下面三项产品决策以及状态文本的位置。
2. 在隔离测试中实现本轮回退、管理员状态转换、轮次标识与去重。
3. 重构 THCCB 等待和取消任务，加入持久记录、对账及旧响应隔离。
4. 接入菜单、状态文本、确认提示、关闭后继续游戏及重连时机。
5. 如选择两端改造，先让 THCCB 提供兼容的新能力，再启用本地对应处理；不把未部署的新接口当作现有能力。
6. 完成测试后再安排运行服务更新，并先检查当时是否存在活动竞猜。正式站核验使用只读操作，不创建正式测试竞猜。

主要验收覆盖：

- 让模拟 THCCB 请求一直悬而未决，关闭联动/作废/重置仍能完成本地响应和界面更新；无需等模拟请求超时。
- 操作正在开盘、封盘、提交结果时执行上述管理动作，迟到的成功和失败响应都不改变新局。
- 关闭再开启发生在不同阶段时，开盘只发生在约定事件；旧退款没处理好时不补开当前轮。
- 作废分别发生在揭晓前、揭晓后、加时和刚判定胜负时，成绩、补轮、复盘和目标采样历史正确。
- 重复取消、结果已提交但响应丢失、404/401/409、未知旧轮、重启后待处理记录恢复。
- 多控制器重复点击和过时命令不会多次随机惩罚、连续作废或污染新轮。
- 若两端配套：用真实并发数据库事务验证“取消先到、开盘后到”以及取消和结算竞争；不能只用 HTTP mock 证明该性质。
- 菜单可用性、移动端布局、监视器无管理权限、未揭晓答案与密钥不泄露；原有正常游戏流程回归。

测试优先扩展已有游戏规则、THCCB 服务端和少量浏览器测试，分别覆盖各自真实风险，不在每层重复同一完整流程。THCCB 的 Python 验证使用项目已指定环境；如没有可确认的环境，实施时先按用户环境约定询问，不自行建环境或装包。

**已批准的三项决策**

1. 揭晓后作废：推荐允许回退本地当前轮，THCCB 已结算奖励保留并明确提示；备选为揭晓后不允许作废。
2. 普通操作推进：推荐正常关键操作等确认、管理员操作立即生效；备选为主游戏始终继续、失败自动取消竞猜。
3. 改造范围：推荐本地与 THCCB 配套改造；备选为本次只改本地并明确兼容限制。

界面位置已确认：状态短句位于游戏操作按钮下方；管理员入口在右上角，替换“重新开始”。三项决策均采用推荐选项，已批准两端实施。
